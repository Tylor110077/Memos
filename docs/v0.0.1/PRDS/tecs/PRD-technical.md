## 2. 技术选型与决策记录

### ADR-001：前端框架

- **背景**：需要全栈能力（前端画布 + 后端 AI 代理）
- **选项**：Next.js / Vite + Express / Remix
- **决定**：Next.js 14 (App Router)
- **后果**：API Routes 处理 AI 代理，无需独立后端服务；Vercel 一键部署

### ADR-002：画布引擎

- **背景**：需要无限画布、节点拖拽、连线、缩放
- **选项**：React Flow / Konva.js / D3.js / 自研 Canvas
- **决定**：React Flow (@xyflow/react)
- **后果**：开箱即用的节点图能力，自定义节点/边灵活；但深度定制（如力导向布局）需额外工作

### ADR-003：状态管理

- **背景**：画布状态、对话状态、UI 状态需分离管理
- **选项**：Zustand / Redux Toolkit / Jotai
- **决定**：Zustand
- **后果**：轻量无 boilerplate，与 React Flow 官方推荐配合

### ADR-004：数据持久化

- **背景**：MVP 阶段无后端数据库需求
- **选项**：IndexedDB (Dexie) / LocalStorage / SQLite (WASM) / 后端 PostgreSQL
- **决定**：IndexedDB via Dexie.js
- **后果**：容量充足（>50MB），支持索引查询，无需服务端；但数据仅限本机浏览器

### ADR-005：AI 接入方式

- **背景**：需流式输出 + 结构化输出，API Key 不能暴露给客户端
- **选项**：客户端直调 / 服务端代理 / BFF 层
- **决定**：Next.js API Route 服务端代理 + Vercel AI SDK
- **后果**：API Key 安全，流式输出封装完善，切换模型仅需改环境变量

### ADR-006：AI 结构化输出

- **背景**：图谱解析、领域生成等需要 AI 返回结构化 JSON
- **选项**：Prompt + JSON.parse / Function Calling / Vercel AI SDK generateObject
- **决定**：Vercel AI SDK `generateObject` + Zod Schema
- **后果**：类型安全的结构化输出，自动重试，Schema 验证

## 4. 数据模型

### 4.1 TypeScript 接口定义

```typescript
// ===== 节点 =====
export type NodeType = 'concept' | 'theme' | 'material' | 'understanding' | 'question';
export type NodeStatus = 'lit' | 'unlit';
export type MaterialType = 'article' | 'video' | 'pdf';

export interface KnowledgeNode {
  id: string;
  type: NodeType;
  title: string;
  content: string;
  level: number;
  status: NodeStatus;
  position: { x: number; y: number };
  parentId?: string;
  metadata: NodeMetadata;
}

export interface NodeMetadata {
  source?: string;
  materialType?: MaterialType;
  conversationId?: string;
  domainId?: string;
  createdAt: string;
  updatedAt: string;
}

// ===== 边 =====
export type EdgeType = 'hierarchy' | 'association' | 'reference';

export interface KnowledgeEdge {
  id: string;
  source: string;
  target: string;
  relation: string;
  type: EdgeType;
  autoGenerated: boolean;
}

// ===== 对话 =====
export type ChatMode = 'learn' | 'feynman' | 'debate' | 'design';

export interface Conversation {
  id: string;
  nodeId?: string;
  mode: ChatMode;
  messages: ChatMessage[];
  createdAt: string;
  updatedAt: string;
}

export interface ChatMessage {
  id: string;
  role: 'user' | 'assistant';
  content: string;
  timestamp: string;
}

// ===== 领域图谱 =====
export interface DomainGraph {
  id: string;
  name: string;
  nodeIds: string[];
  createdAt: string;
}
```

### 4.2 字段说明

| 表 | 字段 | 类型 | 说明 |
|----|------|------|------|
| nodes | id | string (nanoid) | 主键 |
| nodes | type | enum | 节点类型，决定视觉样式 |
| nodes | level | number | 0=领域, 1=主题, 2=子主题, 3+=知识点 |
| nodes | status | enum | lit=已学习, unlit=未点亮（领域模式） |
| nodes | position | {x, y} | 画布绝对坐标 |
| nodes | parentId | string? | 层级父节点（可选，图结构由 edges 维护） |
| edges | type | enum | hierarchy=层级, association=关联, reference=引用 |
| edges | relation | string | 自然语言关系描述 |
| edges | autoGenerated | boolean | 区分 AI 生成 vs 用户手动 |

### 4.3 IndexedDB 索引策略

```typescript
db.version(1).stores({
  nodes: 'id, type, level, status, parentId, metadata.createdAt, metadata.domainId',
  edges: 'id, source, target, type, [source+target]',
  conversations: 'id, nodeId, mode, createdAt',
  domains: 'id, name',
});
```

| 索引 | 用途 |
|------|------|
| nodes.type | 按类型筛选节点 |
| nodes.level | 缩放层级过滤 |
| nodes.status | 领域图谱中筛选未点亮节点 |
| nodes.parentId | 查询子节点 |
| nodes.metadata.domainId | 按领域筛选 |
| edges.[source+target] | 复合索引，快速判断两节点间是否已有连接 |
| conversations.nodeId | 查询节点关联的对话 |

## 7. AI Prompt 工程

### 7.1 学习模式 (learn)

```
你是一位友善的知识讲解者。你的任务是帮助用户理解他们想学的任何知识。

规则：
- 用清晰、有层次的方式讲解，适时提供类比和例子
- 讲完后自然延伸："对了，这个跟 XX 其实有关系，你感兴趣的话我们可以聊聊"
- 不要居高临下，像朋友间分享有趣的知识
- 如果超出知识范围，诚实说明
- 回复使用 Markdown 格式
```

### 7.2 费曼模式 (feynman)

```
你是一位真诚的求知者。用户正在向你讲解他们学到的知识，你要认真倾听。

规则：
- 你是真的想弄懂，不是在考验对方
- 遇到不明白的地方："等等，这个地方我没太想明白……"
- 绝不说"你的理解不完整"或"你错了"
- 如果有不同理解："我之前好像听说的是……跟你说的不太一样，是我记错了还是……？"
- 追问顺着用户思路走，帮助他们自己发现盲区
- 适当表达"哦！我懂了！"的正反馈
- 绝不扮演评判者角色
```

### 7.3 辩论模式 (debate)

```
你是一位聪明但友善的怀疑者。用户将对一个知识观点进行论证。

规则：
- 提出尖锐但有建设性的问题
- 不是要"赢"辩论，而是帮助用户深化理解
- 可以扮演反方："如果有人说……你怎么回应？"
- 追问论据根基："你说 X 导致 Y，但这个因果关系是必然的吗？"
- 适时承认好的论证："这个角度我没想到，有道理"
- 绝不判对错，只推动思考深入
```

### 7.4 设计模式 (design)

```
你是一位协作设计者。用户正在用所学知识设计一个系统或解释一个现象。

规则：
- 引导用户做决策，而非替他们做
- 追问"为什么这样选？有没有考虑过其他方案？"
- 提出真实约束："如果数据量增大 100 倍呢？"
- 帮助用户看到设计中的 trade-off
- 不追求标准答案，关注决策过程的合理性
```

### 7.5 图谱解析 Prompt

```
分析以下对话，提取其中的知识点结构。

已有节点列表（避免重复创建）：
{existingNodes}

对话内容：
{conversation}

请输出：
1. newNodes: 对话中新出现的知识点（不在已有列表中的）
2. updatedNodes: 需要补充内容的已有节点
3. newEdges: 节点间的关系

对于每个新节点，判断其 level：
- 大领域 → 0, 主题分类 → 1, 子主题 → 2, 具体知识点 → 3+

对于每条边，判断类型：
- hierarchy: 上下级/包含关系
- association: 相关/类比/对比关系
- reference: 引用/来源关系
```

## 9. 持久化策略

### 9.1 写穿模式

每次 Store 修改操作同时异步写入 IndexedDB，不阻塞 UI：

```typescript
addNode: (node) => {
  set(state => ({ nodes: [...state.nodes, node] }));
  db.nodes.add(node);  // fire-and-forget
},
```

### 9.2 启动加载

```typescript
initializeGraph: async () => {
  const [nodes, edges] = await Promise.all([
    db.nodes.toArray(),
    db.edges.toArray(),
  ]);
  set({ nodes, edges });
},
```

### 9.3 版本迁移

Dexie 支持 `db.version(n).stores(...)` + `upgrade()` 进行 Schema 迁移，后续版本迭代时添加。

## 10. 错误处理策略

| 场景 | 处理方式 |
|------|----------|
| AI API 超时/失败 | Toast 提示"AI 暂时无法响应，请稍后重试"，不丢失已有对话 |
| 图谱解析失败 | 静默失败，不影响对话体验；可手动重试 |
| IndexedDB 写入失败 | Console 警告 + 内存中数据仍可用（会话内不丢失） |
| 结构化输出格式错误 | AI SDK 自动重试（最多 2 次），仍失败则跳过解析 |
| 网络断开 | 画布操作正常（本地数据），对话功能提示离线 |

## 11. 性能预算

| 图谱解析耗时 | < 10s | 自定义计时 |

## 12. 安全考量

| 风险 | 对策 |
|------|------|
| API Key 泄露 | 仅存于 .env，通过服务端 API Route 代理，客户端不可见 |
| Prompt 注入 | 用户输入作为 message content 传递，不拼入 system prompt |
| XSS | 节点内容渲染使用 Markdown 安全解析（rehype-sanitize） |
| 数据丢失 | MVP 为本地存储，后续版本考虑导出/备份功能 |
